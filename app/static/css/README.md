# Временная методичка по адаптивности: сначала ноутбуки

Статус: рабочие правила для следующих правок CSS, 26.09.2026. Этот файл описывает способ диагностики и критерии результата; сам по себе он не меняет вёрстку. Примеры на скриншотах пользователя — ориентиры для проверки, а не доказательство конкретной причины в текущем локальном коде.

## Базовый принцип

Адаптируем **содержимое к доступному месту**, а не страницу к названию устройства. Ноутбук с масштабом 125% может иметь меньше CSS-пикселей, чем ожидается по физическому разрешению экрана. Точку переключения выбираем там, где конкретный блок перестаёт нормально помещаться, а не по списку популярных моделей. Сначала делаем ширины и сетки гибкими, потом добавляем необходимые media queries. [web.dev: Responsive web design basics](https://web.dev/articles/responsive-web-design-basics), [MDN: Responsive design](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design).

## Правила для реализации

1. **Измерять CSS viewport.** Перед исправлением записать `innerWidth × innerHeight`, `devicePixelRatio`, масштаб браузера и размеры проблемного блока. Разрешение PNG или экрана не равно области страницы: её уменьшают панели браузера, масштаб и настройки дисплея. Горизонтальный и вертикальный пределы проверять отдельно. [web.dev](https://web.dev/articles/responsive-web-design-basics).
2. **Сначала найти первый переполненный контейнер.** В DevTools посмотреть computed `width`, `min-width`, `height`, `min-height`, `overflow`, `position`, `transform`, а также применившееся правило и файл. Исправлять ограничение у источника переполнения. Скрытие лишнего через `overflow: hidden`, уменьшение всей секции `transform: scale()` или глобальное снижение шрифта маскируют проблему и могут обрезать содержание.
3. **Строить гибкую композицию.** Ограничивать общую ширину через `max-width`, внутренние поля делать адаптивными; для колонок использовать Grid/Flex и разумную минимальную ширину каждой смысловой части. У Grid колонка `1fr` может сохранять минимальную ширину содержимого; при необходимости применять `minmax(0, 1fr)`. У детей Flex/Grid проверять `min-width: 0`, когда длинный текст или код выталкивает соседнюю колонку. Переключать 3→2→1 колонки в точке, где карточки теряют читаемость. [MDN: Grid](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Grids), [MDN: minmax()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/minmax), [MDN: flex](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/flex).
4. **Высоту считать ограниченным ресурсом, но не запирать текст.** У насыщенной контентом секции предпочитать `min-height` и естественный рост; страница может прокручиваться. `height: 100vh`, `max-height: var(--viewport-height)` и `overflow: hidden` допустимы только после проверки, что при малой высоте и увеличенном тексте ничто не обрезается. Если нужна высота видимой области, учитывать динамическую панель браузера и различие `vh`/`svh`/`dvh`; это не замена естественной высоте текста. [MDN: viewport units](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length), [W3C: G179](https://www.w3.org/WAI/WCAG22/Techniques/general/G179.html).
5. **Не превращать текст в узкую колонку.** Сначала дать текстовому блоку достаточную ширину и изменить сетку; только затем умеренно менять размер заголовка, отступы и межколоночный промежуток. Для заголовков можно использовать ограниченный `clamp()`; для основного текста сохранять читаемый размер и высоту строки без жёсткой привязки к `vw`. Не задавать размер шрифта только в `vw`: при увеличении страницы текст может вести себя не так, как ожидается. Проверять длинные слова, цифры, кнопки и русские фразы. [web.dev: Typography](https://web.dev/learn/design/typography), [web.dev: Fluid type](https://web.dev/articles/baseline-in-action-fluid-type), [W3C: Resize Text](https://www.w3.org/WAI/WCAG21/Understanding/resize-text).
6. **Сохранять пропорции и смысл фотографии.** Для обычной картинки: `max-width: 100%; height: auto`. Для кадра заданной формы: размер контейнера или `aspect-ratio`, затем `object-fit: cover` (преднамеренная обрезка) и `object-position` с учётом лица/важной детали. Если кадр нельзя обрезать, использовать `contain` или иной формат блока. Проверять изображения после смены числа колонок и при низкой высоте окна. При наличии вариантов файлов `srcset`/`sizes` выбирают подходящее разрешение, а `<picture>` — другой кадр для другого макета; это отдельная задача от геометрии CSS. [MDN: Images and media](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Images_media_forms), [MDN: object-fit](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/object-fit), [MDN: Responsive images](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images).
7. **Компонент зависит от своего места.** Страница меняет общую сетку по ширине окна; карточка, которая бывает и в широкой, и в узкой колонке, может менять внутренний макет по ширине собственного контейнера через container query. Не добавлять container query без реального сценария повторного использования. [MDN: Container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries).
8. **Доступность — часть проверки.** При увеличении текста до 200% он не должен пропадать или перекрывать элементы. При масштабе страницы до 400% эквивалентная ширина для проверки reflow — 320 CSS px: основное содержимое и функции должны оставаться доступны без горизонтальной прокрутки (кроме элементов, для которых двухмерная раскладка необходима). Это стандартная общая проверка, даже если текущий этап посвящён ноутбукам. [WCAG 2.2: 1.4.4 и 1.4.10](https://www.w3.org/TR/WCAG22/).

## Как применять к этой кодовой базе

- `styles.css` загружается перед `laptops.css`, затем идут `desktops.css`, `tvs.css`, `phones.css` (`app/templates/base.html`). Итог определяется **всем каскадом**: порядок файлов, media query, специфичность и `!important`. После каждой правки проверять computed style нужного элемента, а не только текст последнего файла. Уже была регрессия размера текста в блоке опыта работы после пересечения правил.
- В `main.js` атрибут `data-viewport` выставляется по `innerWidth`: `mobile` до 768, `tablet` до 1180, `desktop` 1181–1599, `wide` от 1600 CSS px. Эти имена — категории в коде, а не достоверное определение физического устройства. Правила `laptops.css` с `min-width: 900px` и селекторами `desktop`/`wide` действуют также на часть планшетных и больших экранов. Для каждого изменения явно определять диапазон воздействия и проверять соседние размеры.
- В `laptops.css` уже есть сочетания ограничений по ширине и высоте, `max-height: var(--viewport-height)`, `overflow: hidden`, `transform` и `!important`. Это **кандидаты на проверку**, а не установленная причина всех дефектов на скриншотах. Не наращивать поверх них универсальные переопределения: сперва выяснить, какое конкретное правило ломает конкретный блок.
- Для каждой секции держать один понятный набор базовых правил и минимальное число поправок по реальным точкам перелома. Общий стиль элемента не дублировать в правилах для нескольких ширин, если его можно оставить в `styles.css`. Исправляя ноутбук, повторно проверять широкие мониторы, поскольку диапазоны сейчас пересекаются.

## Порядок работы над одним дефектом

1. Открыть локальную страницу на точном CSS viewport, записать масштаб и сделать скриншот. Сопоставить с присланным примером. При сравнении с `pymentor.ru` учитывать, что опубликованная и локальная версии могут различаться.
2. Найти первый элемент, который выходит за доступную ширину/высоту, или первый текстовый блок, ставший чрезмерно узким. Посмотреть его родителя и действующее правило.
3. Исправить причину в порядке: ограничение контейнера → сетка и минимальные ширины → интервалы → размер заголовка/изображения. Уменьшение обычного текста оставлять последним и не доводить до нечитаемости.
4. Проверить до/после на соседних ширинах, небольшой высоте, увеличенном тексте и клавиатурной навигации. После исправления одной секции просмотреть все остальные: правила в `laptops.css` нередко затрагивают несколько секций.

## Матрица проверки ноутбуков

Это **контрольные размеры CSS viewport**, а не список обязательных брейкпоинтов: `1280×720`, `1366×768`, `1440×900`, `1536×864`, `1600×900`, `1920×1080`. При ограниченном времени начать с `1366×768`, `1440×900`, `1920×1080` и дополнительно проверять границы существующих условий: `899/900`, `1180/1181`, `1199/1200`, `1439/1440/1441`, `1599/1600` CSS px. Высоту тестировать отдельно, особенно около `760`, `800`, `900`, `920` px. `2560×1440` из скриншотов — соседний широкий контроль, чтобы ноутбучная правка не испортила мониторный вариант.

| Область | Что должно быть видно и работать |
| --- | --- |
| Шапка | Имя, навигация и кнопка не обрезаны и не перекрываются; активный пункт заметен. |
| Первый экран | Заголовок, описание, обе основные кнопки и карточка ментора читаемы; портрет без искажения. Ниже экрана может быть контент, доступный прокруткой. |
| Программа | Список этапов и правая панель сохраняют читаемую ширину; длинные названия не превращаются в «лесенку»; нижний результат доступен. |
| Истории и фото | Лица и подписи видны; карточки не растягивают страницу непропорционально и не режут важные части фото. |
| Карьера и тарифы | Карточки, цены, описание опыта и кнопки не перекрываются; основной текст одного уровня имеет согласованный размер. |
| Вся страница | Нет непреднамеренной горизонтальной прокрутки, обрезанных интерактивных элементов и текста, который превращается в один-два слова на строку из-за слишком узкой колонки. |

Критерий готовности каждой правки: исправленный блок проходит матрицу на целевом и соседних размерах; функциональность и читаемость сохраняются при 125%, 150% и 200% масштабе; проверка computed styles подтверждает, что изменение пришло из ожидаемого правила. При необходимости зафиксировать пару скриншотов «до/после» с указанным CSS viewport.
